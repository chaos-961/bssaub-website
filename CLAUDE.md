# BSS AUB Website

Rebuild of bssaub.com for the AUB Business Student Society. One goal drives every decision: get an AUB student to grab the membership card. Everything else (sponsors, story, animations) exists to make that decision feel obvious.

Repo: `https://github.com/chaos-961/bssaub-website.git` · Live: `https://chaos-961.github.io/bssaub-website/` (GitHub Pages via Actions; custom domain later).
Current version: **0.5.0**.

## Rules (standing, no exceptions)

1. **Git gate.** Never commit or push unless the user explicitly says commit or push in that session. "Looks good" is not authorization. Every push to `main` auto-deploys — treat push authorization as deploy authorization and say so.
2. **Version contract.** Bump `version.json` by +0.0.1 as part of each authorized push (base-10 carry: 0.0.9 → 0.1.0). Keep the three static badge fallbacks (index/404/account footers) in sync with it (two between v0.4.1 and v0.4.2, while the account page was gone; `admin.html` carries no footer and no badge, deliberately). Commit message format: `v0.1.3: short description`.
3. **No invented data.** Discounts, Instagram links, and redemption steps are never guessed. Unknown means blocked and listed, never filled with plausible garbage. Nothing marked "?" ever ships.
4. **No hyphens or dashes in user-visible copy.** Em dashes become commas, colons, or periods; titles join with "·"; compounds get rephrased ("hub led by students", not "student-led hub"). Applies to text nodes, aria-labels, alt text, titles, and meta.
5. **File content edits via the Edit/Write tools only.** PowerShell 5.1 text operations mojibake UTF-8.
6. **Feel checks on real hardware are the user's.** Headless verification covers logic, geometry, and colors; 60fps judgment is theirs.
7. **Session protocol.** Read this file, state version + open items in a line or two, await instruction. A user request is its own authorization — the rules stop AI initiative, not user freedom. Keep the version line and Open items section here current as work ships.
8. **Admin re-encrypt on every push** (user instruction, 2026-07-27). If `src/admin/dashboard.html` or `dashboard.js` changed at any point in the session, run `BSS_ADMIN_PASSWORD=... BSS_ADMIN_EMAIL=... npm run admin:payload` as part of the authorized push, so the shipped ciphertext is the shipped source. **Both env vars are required since v0.4.8** (the admin's Firebase address rides inside the ciphertext); the encryptor refuses to write without either, and note the build gate cannot catch a changed EMAIL because the address is deliberately not part of the published source hash. Never push a stale payload and never hand back an admin change without the regenerated `public/admin-payload.json` beside it. `scripts/check-admin-payload.mjs` enforces this at build time (it has already caught it once) but the rule is on the push, not on the build, because a forgotten re-encrypt deploys an admin that unlocks into the PREVIOUS build with no error anywhere. The password is the user's and lives nowhere in this repo, so ask for it if it is not already in the session.

## Stack and shape

Vanilla JS + Vite 6 (`index.html` + `account.html` + `admin.html` + `404.html`; multi-page since the start) · GSAP + ScrollTrigger · Lenis smooth scroll · Matter.js physics · **Firebase Auth (v0.4.2) + Firestore Lite (v0.4.8), on the account and admin pages only, every piece behind a dynamic import** · Fraunces + Instrument Sans (self-hosted variable woff2). No other runtime deps, zero third-party scripts.

- `src/main.js` — init order matters: scroll → oceanMesh → nav → heroCard → cardName → modal → perkField → journey → sponsorCta → agencyCredit → **reveal** → footerVersion → `scroll.refresh()` → preloader last (it collects `[data-preload]` images once the page above it has been laid out). `initPerkField` is **async** since v0.4.6 (Matter.js moved to its own chunk) and this order still holds unchanged, because an async function runs synchronously up to its first `await` and that `await` sits after the DOM build, the layout and the reduced-motion return: only the physics resumes late. The preloader `onComplete` fires `heroCard.enter()`. `reveal` goes after the field and the journey because its triggers measure elements those two have just laid out; `oceanMesh` now takes `scroll` purely to read its velocity (v0.3.6 surge) and still owns no part of the page's scroll behavior. (The generative starfield background lived in this order until v0.2.5; it was extracted to the `Background Constellation` template and removed.)
- `src/data/sponsors.js` — single source of truth for every sponsor. `src/data/names.js` — the 100 first names the hero card types onto itself (v0.3.9).
- `src/modules/*` — one module per concern; `src/styles/*` — tokens.css first, then per-section files. The v0.4.2 additions: `session.js` (the display-name cookie, no Firebase, shared by index and account), `loginToast.js` + `toast.css` (the greeting), `accountAuth.js` + `auth.css` (the member page, and `auth.css` is shared with the admin gate so its primitives are named card/field/tab rather than for either page), `src/data/firebase.js` (project config, public by design), and `src/admin/*` (the plaintext dashboard that is never served). The v0.4.8 additions: `src/data/membership.js` (**imports nothing**, so all three consumers can share it, the blob-module dashboard included) and `memberPanel.js` (the card on the account page). `firestore.rules` is **gitignored on the user's call**: it names the admin account's address, and the console is where rules actually live, so the repo copy would be exposure with no benefit.
- `public/assets/` — brand/, card/, sponsors/<category>/<id>.webp, journey/.
- `src/assets/bg/mesh.svg` — the generated background mesh. It lives in `src/`, not `public/`, so Vite resolves, hashes, and base-rewrites the `url()` in site-bg.css; a `public/` file would have to hardcode `/bssaub-website/` and break on the custom-domain flip. Regenerate with `node scripts/generate-bg-mesh.mjs [#hex]` (seeded, so output is byte identical unless the base changes). Never hand edit the SVG.
- `src/lib/mesh.js` — **the single source of truth for the mesh**: geometry, the palette ramp, the drift cycle, the swell field, and the contrast maths. Imported by `scripts/generate-bg-mesh.mjs` (writes the shipped SVG), `scripts/check-swell.mjs` (the motion gate), and `src/modules/oceanMesh.js` (builds the WebGL buffers). Never reimplement or approximate it in a second place: the static SVG is the animation's **rest state**, and if the two drifted the background would visibly jump as the canvas fades in. `DEFAULT_BASE` must stay equal to `PALETTE_CYCLE[0]` for the same reason; the build script hard fails if they differ. **Recoloring the background is one edit**: those values, then rerun the script.
  - The swell is data, not code (v0.3.4): `SWELL` is a table of sum-of-sines terms, and `swellGlsl()` **generates the shader's `swell()` function from it** while `swellAt()` evaluates the same table in JS. That is why the amplitude proof is trustworthy: the harness and the shipped shader are the same numbers by construction, not by careful copying. Verified on a real GPU at v0.3.4, agreeing to within 8 bit encoding precision (max error 0.007). Never hand edit `swell()` inside oceanMesh.js.
  - Two gates guard this file, and **both must be re-run after touching `AMP`, `SWELL`, `MESH`, or `PALETTE_CYCLE`**:
    - **Colour**, in `generate-bg-mesh.mjs`, which **refuses to write** on failure (exits 1, leaves the asset untouched), so an illegible colour cannot reach the repo by accident. It checks the still *and* the worst instant of the animated cycle with the shader dither applied. `--ink-soft` body copy on the darkest facet is the binding number, floor 4.5:1. A dev-only `COLORS` picker panel existed briefly at v0.3.2 and was removed the same day on the user's word; do not rebuild it without a fresh brief.
    - **Motion**, in `scripts/check-swell.mjs` (v0.3.4), which walks the real lattice through a 240s sweep at both the desktop amplitude and the capped mobile one and fails on any inverted facet, on any facet squashed below half its rest area, or on an overscan margin too small for the worst case displacement. This is not ceremony: it **rejected the first v0.3.4 attempt** (a facet collapsed to 0.36 of rest, which reads as a crease), and the fix it forced (longer wavelengths, not lower amplitude) is what let the motion get 3x stronger at all.
- Deploy: `.github/workflows/static.yml` (push to main → build → Pages). `vite.config.js` has `base: '/bssaub-website/'`. Custom-domain flip: CNAME in public/, base to `/`, revisit 404.html's absolute icon paths.
- Clean URLs (v0.1.3, retired at v0.4.1, **back at v0.4.2**): internal links are extensionless (`account`, never `account.html`), with a `cleanUrls` middleware in `vite.config.js` giving dev and preview the behavior Pages has natively. Index and 404 need no rewrite. `CLEAN_PAGES` now holds `account` and `admin`; **a new page that wants an extensionless link adds itself there**, or it 404s in dev while working fine on Pages, and its canonical and og:url use the extensionless form. The font preload plugin came back in the same pass and now serves both gated pages.
- **CSP (v0.4.2), on account and admin only, injected at BUILD time by a `vite.config.js` plugin.** It is written there rather than into the HTML because Vite's dev server serves an inline module script (its HMR client), so a `script-src 'self'` meta tag in the source file would break `npm run dev` while looking perfect in production; `ctx.bundle` is present in build and absent in dev, which is the switch. Neither page carries **any** inline `<script>` for this reason (their `js` and `reduced-motion` root classes are set at the top of the entry module instead; index keeps its inline version because there the class gates the preloader curtain, which must be up before the bundle arrives). `style-src` keeps `'unsafe-inline'` on purpose, since GSAP writes element styles and CSS injection is not the surface worth a rewrite once script execution is locked. `frame-ancestors` is **ignored in a meta CSP by spec** and GitHub Pages cannot set headers, so clickjacking is covered by the frame bust at the bottom of `src/admin.js`. Verified in `vite preview`: zero console errors on either page, and the injected tag lands at byte 642 (account) and 466 (admin), which keeps the charset meta inside the first 1024 bytes the parser needs it in.
- Local run: `run-local.bat` (untracked, gitignored — user helper): opens the already-running server if 5173 is busy, else installs deps if needed and starts `vite --open`.

- **Background (v0.3.1, user brief): a low poly triangle mesh**, `div.site-bg` first in `<body>` on every page, styled by `src/styles/site-bg.css`, imported by all four entries (main.js, page.js, account.js, admin.js). One fixed viewport-sized layer at `z-index -1`; `body` is `background: transparent` so it shows through, and `html` keeps the flat `--bg` for the overscroll gutter and as the load-failure fallback. Fixed rather than a document-tall background because stretching the mesh down a 10x-viewport page smears the facets into ribbons, and a fixed layer that never moves is the cheapest thing the compositor can hold. The **grain moved here from `body`** and rides as a second background layer at `background-blend-mode: multiply`; its noise tile is pre-compressed into `[0.94, 1.0]` by an `feComponentTransfer` in the data URI, because the old "dilute with a flat `--bg` layer on top" trick only works over a flat ground and would have washed the mesh 86% toward white.

  - Square 1400x1400 source with `background-size: cover` so it crops gently in both orientations (a landscape source would double the facet size on portrait phones). Facets land ~41px on a 375px phone and ~64 to 128px on desktop, i.e. 9 to 20 across, bracketing the ~12 of the brief's reference. `height: 100lvh` so a retracting mobile URL bar cannot expose a strip. ~8.5KB gz, vector so one file is exact at every DPR.
  - Cost of the static layer: no JS, no animation, no `mix-blend-mode`, no `backdrop-filter`. Painted once and re-used as content scrolls over it.
- **The ocean layer (v0.3.2, user brief: the mesh should swell like water and the color should drift).** `src/modules/oceanMesh.js` adds `canvas.site-bg__canvas` inside `div.site-bg` and animates the same lattice in WebGL. The static SVG **stays underneath as the floor** and is what paints pre-bundle, with JS off, under `prefers-reduced-motion`, when WebGL is missing, and on context loss; the canvas only gets `is-live` (opacity 1) after frame zero is drawn, so there is no flash and the crossfade is between two states of one mesh, not two designs.
  - **WebGL is the cheap option here, not the expensive one.** Canvas 2D would mean 800 `fill()` calls per frame on the main thread, competing with Lenis, GSAP and the Matter.js field; SVG/CSS cannot move vertices at all. WebGL is one draw call of 2400 vertices with displacement in the vertex shader. Measured: draw submission ~0.0003ms, and the fragment shader is one varying plus a hash.
  - What holds the cost down, all of it load bearing: **one draw call**, buffers uploaded once (only uniforms change per frame), **30fps cap**, backing store pinned to **DPR 1** (adjacent facets differ by a few levels so there is nothing for extra resolution to sharpen, and it is a 4x fragment saving on 2x displays), fully parked on `visibilitychange`, and parked on context loss until it is restored. **Do not add a per frame `getBoundingClientRect`** — sizing is driven by a debounced `ResizeObserver`, because reading layout every frame would make the background the most expensive thing on the page. Note that none of the v0.3.4 changes cost a frame: bigger amplitude and a wider palette are different numbers in the same uniforms, not more work.
  - Sizing uses `ResizeObserver` on the canvas, not a window `resize` listener: this fixed layer changes width by the scrollbar once the perk field grows the page past one screen, which no window event reports.
  - **Not weird** is a verified property, not a hope, and `scripts/check-swell.mjs` is where it is verified. Amplitude is **13.5 mesh units** against a 70 unit cell (7 through v0.3.3, 18 at v0.3.4, trimmed 25% at v0.3.5 on the user's word): measured peak vertex displacement 37.1 units, **52.9% of a cell**, with **zero inverted facets** and the smallest facet holding 0.799x its rest area (0.771x at the mobile cap). Drawn at `OVERSCAN` 1.08 (56 units of margin against a 30 unit worst case), verified empirically at v0.3.4 too: zero edge gap pixels over 150 frame sweeps at 1440x900, 390x844 and 844x390, and the margin only got safer since.
  - **The lever that made the motion 3x stronger was WAVELENGTH, not amplitude.** Facets tangle on the local *shear* of the displacement field, not on how far it travels, so long waves let neighbouring vertices move together and the surface heaves as one body. The first v0.3.4 attempt kept the v0.3.2 wavelengths and just raised amplitude; the gate failed it at 0.36x rest area. Stretching every wavenumber by 1/0.7 at the same amplitude took the same motion to 0.74x. If more power is ever wanted again, lengthen the waves first.
  - Colour drift walks `PALETTE_CYCLE` over **64s** (96s and three stops through v0.3.3), now **four stops spread across the wheel**: rose, cool lavender, warm apricot, soft mauve, all within ~0.01 relative luminance of each other. Equal luminance is the whole trick, it is what lets the hue travel this far without moving the contrast budget. The stop order is chosen so every crossfade *midpoint* lands back in the rose family, so the extremes read as the page leaning warm or cool and the crossings read as home. Plus a **±0.15** slide of the ramp itself (±0.06 before) so light appears to move across the surface; it is bounded and the ramp clamps, so the deep end still resolves to the same stop.
  - **Contrast is measured against rendered pixels, not stop values.** At v0.3.4 the whole cycle was rendered on a GPU at three viewports and every pixel read back: darkest rendered pixel `rgb(220,191,202)`, giving `--ink-soft` **4.76:1**, `--ink` 10.57:1, `--accent` 5.61:1. Above the 4.5:1 AA floor at every instant, at every viewport.
  - **Mobile (v0.3.4, user report that none of this happened on a phone).** Three causes, only one of them fatal. (1) **Context loss was terminal**: mobile GPUs drop WebGL contexts routinely when you leave the tab, and the old handler revealed the static mesh and never came back, so a phone typically animated once per page load and then looked permanently still. `webglcontextrestored` now rebuilds the program and buffers, re-fits, and eases the swell back up from flat. This was the actual bug. (2) **A 30Hz device ran at 15fps**: Low Power Mode and battery savers cap rAF at 30fps, which lands just under this module's own 30fps gate once timer coarsening applies, so every second frame was rejected; `FRAME_SLACK` (2ms) fixes it. (3) **The motion was half size in pixels**: `cover` renders the mesh at scale ~0.60 on a phone against ~1.03 on a desktop, so amplitude now compensates for the fit scale, capped at `AMP_SCALE_MAX` 1.15 because the no-inversion proof is written in mesh units and this is what inflates them. Net motion in CSS pixels: **41px desktop, 28px phone** at the v0.3.5 amplitude (55px and 37px at v0.3.4, 17px and 10px before it).
  - The swell now **eases up from flat over 1.6s** (`WAKE_S`), which makes frame zero pixel identical to the static SVG underneath, so the 0.7s reveal is a true crossfade with nothing to jump. Re-run on context restore for the same reason. Before v0.3.4 frame zero was already displaced, which was invisible at amplitude 7 and would not have been at 18.

### Scroll motion system (v0.3.6, user brief: scroll driven animations that look expensive, behave the same on phone and desktop, and stay cheap)

Eleven animations, all scroll driven, all identical at every width (no desktop only or mobile only path anywhere in this set). **Nine of these eleven survive; v0.5.0 added ten more on the same shape and to the same budget discipline, and its entry below is where the exit system, the strand guard and the transform channel accounting live.** **The shape of the implementation is the point**: the JS budget had ~5.5KB gz of head room, so nothing here re-implements in JavaScript what CSS already does free. One shot reveals are a single `.is-in` class and the entire look, including the per element stagger, is CSS (`--i` on the child, one `transition-delay` calc in `reveal.css`). Only genuinely scrubbed work gets a frame loop, and every scrubbed animation moves exactly one composited property on one element. Net cost: **+1.3KB gz JS, +0.9KB gz CSS**.

Files: `src/modules/reveal.js` + `src/styles/reveal.css` carry the shared primitives (`.rv-mask`, `.rv-up`, `.rv-rule`, `.is-drawn`); the rest live in the module that owns the element.

1. **Bubble genesis** (the user's headline ask at v0.3.6) — see the Perk Field entry below. The burst half of it was removed at v0.4.4, also on the user's word.
2. ~~**Hero departure**~~ — the hero copy lifting 64px and fading to 0.12 as you left the section. **Gone entirely at v0.4.5** on the user's word ("there is weird effect of like fading away when I scroll, remove it"); the card half went at v0.4.0 on the same complaint about the card. Nothing in the hero is keyed to scroll now. The card's removal is the part worth keeping: fading a wrapper that was an ancestor of `.hero-card__tilt`'s then `preserve-3d` subtree made the browser composite the card's layers separately, so on a phone the background mesh read straight through the card. See the v0.4.0 entry below, and the header comment at item 4 in reveal.js.

3. **`/admin`, the encrypted gate (the pavialeb.com shape).** Behind it, nothing but a sign out, per the brief.

   - **The dashboard is ENCRYPTED, not password checked, and the difference is the whole design.** On a static site a gate of the shape `if (typed === SECRET)` ships the answer to anyone with devtools, and hashing the comparison only moves the problem: the attacker skips the check and reads the markup that was in the bundle all along. ### v0.4.8 (2026-07-28, the membership pass: the admin subscribes people by the month, the account page shows the card only while it runs)

One brief with two ends. The admin gets a search bar with a Search button on its right, results a name can be found in, and per result: add a month, remove a month, delete behind a confirmation, and how many days are left. The account page shows the membership card with the member's own name on it when their subscription is live, and hides it the instant it is not.

**The shape of it, and the one decision everything else follows from: Firestore rules are the authority, not any page.** A static site cannot check anything an attacker cannot patch out, so the admin gate signs in to a real Firebase account and every read and write is checked server side against the address on the ID token. That is what makes "a member cannot grant themselves a membership" a fact rather than a hope. The encryption is still worth what it always was (a stranger cannot read the dashboard) and it is no longer the only thing standing there.

1. **The record: `members/{uid}`, five fields, and a member can create their own but never move its expiry.** `name`, `email`, `searchKeys`, `expiresAt` (epoch ms, 0 meaning none), `createdAt`. The account page writes the row on first sign in with `expiresAt: 0` and the rules refuse any other value on create; on update the rules require `expiresAt` to come back unchanged, so a member can correct their own name (which the admin searches on) and nothing else. `get` is self or admin, **`list` is admin alone**, which is the split that stops one signed in member pulling the whole collection with a single query.
   - **The clock is the visitor's, and that is a bounded, written down weakness.** A member who winds their machine forward can reveal their own card after it lapsed. What that buys is a picture of a card and a link to a form that is public on every page of this site, because the card is honoured in person and not by this page. Reading a trusted time needs a server.
   - `firestore.rules` is the local copy to paste from and is **gitignored** (user's call): rules are never served to a browser, so the admin address is safe inside the console and pointless to publish here.
2. **Search is ONE query and needs NO composite index**, which is what lets the whole feature work the moment the rules are pasted in with no console index step. `searchKeys` holds every prefix of every word in a name (capped at 16 characters and 60 entries), so "khal" finds "Ahmad Khalil" through a single `array-contains`, narrowed client side for exactness so word order does not matter and a word matching nothing rejects the row. An address search runs a range on `email` instead. Both are single field indexes, which Firestore maintains on its own. Names are normalized through one function for storing and for searching, accents stripped, because the admin types from memory rather than copying from the record.
   - The 50 row cap is **reported when it bites** rather than silently trimmed, per the standing no-silent-caps line: a search that hides someone is the one failure nobody notices.
3. **One password, two jobs, and the trade is written down rather than assumed.** The admin's Firebase address travels inside the ciphertext (`BSS_ADMIN_EMAIL` at encrypt time) and the password that decrypts the payload is the same one that signs the account in, so the operator types one thing. That moves what a cracked payload is worth from "some markup" to "write access to the members collection", which is exactly why the old note about password length stopped being theoretical. The mitigation is length and it is the user's to apply.
   - Three things keep the admin session small, all deliberate: a **named** Firebase app (`bss-admin`), so it cannot touch the member session the account page keeps in this same origin's IndexedDB, since the auth store is keyed by app name; **inMemoryPersistence**, so nothing about it is ever written to disk and closing the tab is a sign out; and **the idle lock signs it out and deletes the app**, so a locked admin is a signed out one rather than a hidden one.
   - The connection is started at unlock but **not awaited**, so a slow round trip cannot hold the dashboard shut. The search area waits on the promise instead. A failure there says so honestly and blames the account, not the typing: the payload has already decrypted, so the password was right.
4. **Optimizations, in the order they are worth anything.** `firebase/firestore/lite` rather than the full SDK, which is 33.2KB gz against roughly 90 for a page that does one read and at most one write and wants no live listener. **Firestore is fetched on the first membership read and never before**, so a signed out visitor to the account page (the common case, it is the sign in page) does not pay for it: verified on the built output, auth and core arrive and the 146KB firestore chunk does not. The account page writes only when the name or email actually changed, since the free tier's write allowance is under half its read allowance. And the search index means no composite index and one query per search.
5. **The card on the account page reuses the hero's own geometry**, so its alignment is a construction rather than a tuning job: the SVG viewBox IS the artwork's 663x473 pixel grid (see cardName.js), at `inset: 0` because this card has no border. Measured: the overlay matches the image to 0.02px, the name centres on the rule to 0.2px, and the two unit ratios agree, so `preserveAspectRatio="none"` is not distorting anything.
   - It differs from the hero in one way that matters: **it fits the text.** The hero prints first names off a list whose widest uses 47% of the rule; this prints whatever a real person typed. So it shrinks linearly to fit and squeezes with `textLength` only at the 12 unit floor. Measured: "Ahmad Khalil" 120.4 units untouched, "Abdulrahman Constantinopoulos" 301.1 down to exactly 190 at size 12.3, "Maria Antoinette Bou Khalil Haddad" to the floor and then exactly 190. `getComputedTextLength` returns 0 inside `display: none`, which is why the card is unhidden before the fit and not after.

### v0.4.9 (2026-07-28, four user calls on top of v0.4.8)

1. **Delete now removes the person, not just their row**, and the shape of it is the interesting part. A static site cannot delete a Firebase Auth account: that needs the Admin SDK on a server, or the account deleting ITSELF while signed in. Deleting only the record would have been worse than nothing, because the account page recreates a missing row on the next visit, so the delete would silently undo itself.
   - So Delete **replaces** the record with a `{ revoked: true }` tombstone, and that one field does three jobs. It drops them out of every search (a tombstone carries no `searchKeys` and no `email`, so neither query can match it). It **cannot be written over by the member**, which the existing rules already enforce with no new rule needed: create is refused because the document exists, and update is refused because `shape()` rejects the extra field and their `expiresAt` would have to equal a field the tombstone does not carry. And it is the instruction the account page acts on, deleting its own Auth account the next time that person opens the site.
   - `deleteUser` is attempted, not required: a session more than a few minutes old cannot delete itself without a fresh sign in, and there is no sense marching someone through one to complete their own removal. Either way they are signed out, told the account has been removed, and locked out permanently, because the tombstone outlives the attempt. The residue is an orphaned one field document when the Auth account does go; it is invisible to search and to every reader, and cleaning it is not worth a code path that could resurrect somebody.
   - **The one thing this is not: a ban on the address.** Once the Auth account is gone the email is free, so the same person can register again as a new UID with zero days. That is the right default (delete removes a membership and an identity, not a right to exist) but it is worth knowing before promising otherwise.
2. **Nothing about the backend appears anywhere a visitor can read** (user instruction, and "the website" explicitly includes the screens only the admin sees). ## Sponsor data

One object in `src/data/sponsors.js` + one image = a new sponsor. ## Budgets and floors

- LCP under 2.5s on throttled 4G (live median 1.91s measured at v0.0.2) · CLS ~0 (all media has reserved dimensions).
- JS ≤ **256KB gz**, measured on **index**, which is the page the ceiling was ever about — **96.3KB at v0.5.0, of which only 69.3KB blocks the hero** (95.9 / 68.9 at v0.4.8; the v0.5.0 scroll animation pass is the +0.4, ten animations for less than half a kilobyte, which is the v0.3.6 shape holding for the third time) (98.2 total / 70.5 blocking at v0.4.6 and v0.4.7, 97.7 at v0.4.5, 98.3 at v0.4.4, 95.7 at v0.4.2, 96.4 at v0.4.1, 97.0 at v0.4.0, 95.9 at v0.3.8, 95.7 at v0.3.6, 94.4 at v0.3.4/v0.3.5). Index went DOWN 2.3KB at v0.4.8 while gaining nothing and losing nothing, which is the v0.4.1 and v0.4.2 lesson for the third time: a new shared consumer (membership.js, on two pages) moves a chunk boundary, and index stops paying for parts of a vendor chunk it never used. **Do not read a changed chunk filename or a moved number as a regression; measure the page.** **v0.4.6 split the number in two and that is now the number that matters**: Matter.js is a lazy 27.7KB gz chunk fetched after the entry has run, so the total is flat while the blocking path dropped 27.2KB gz. A reduced-motion visitor never downloads it at all. From here on, quote both halves; a total alone hides whether a feature landed in front of the hero or behind it. The +2.6 spans two versions, since v0.4.3 was never measured; in v0.4.4 it buys the scrubbed text system and the mobile rail wander against what the bubble burst gave back. The other pages at **v0.4.8**, and these now have to be quoted in three parts because that is how they actually load: **account 60.6KB gz of shell, plus 49.7 of Firebase Auth once the SDK lands, plus 33.2 of Firestore Lite ONLY for a signed in visitor** (143.5 all in; the shell's ~52KB is the GSAP/Lenis vendor chunk index has already cached for anyone arriving through the nav link, which is the normal path). **Admin is 8.5KB gz locked** and 91.4 all in, every byte of Firebase arriving after the password. The v0.4.2 index number goes DOWN despite gaining the toast, and the reason is structural rather than a diet, the v0.4.1 note run backwards: a second GSAP/Lenis consumer exists again, so Rollup splits the vendor chunk back out and index no longer pays for the parts of it that only the nav uses. **Do not read a changed chunk filename as a regression; measure the page.** **Raised from 100KB on the user's explicit call, 2026-07-26**, which is the fresh call the old note demanded; the ceiling had been questioned on 2026-07-25 and kept once already.
